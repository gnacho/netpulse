Agentes externos

Cuatro integraciones consultan routers o controladores y envían los datos a NetPulse por HTTPS. El supervisor y las instrucciones viven en un repositorio separado.

MikroTik RouterOS 7+

Consulta RouterOS y envía hosts, puntos de acceso y puertos.

  • Usuario de solo lectura y un equipo para el supervisor
  • API binaria en el puerto 8728, con REST como reserva
  • WiFi Wave2 anuncia la interfaz wifi, no capsman

Asuswrt y Asuswrt-Merlin

El pusher corre en el router y reutiliza las sondas portables de NetPulse. Puede residir en /jffs.

  • Acceso SSH y espacio persistente en /jffs
  • Clientes, radios, canales y puertos Ethernet
  • La cobertura depende del firmware y de las herramientas instaladas

Bouygues BBox

Consulta la API local de la BBox y envía sistema, WAN, hosts activos y tasas de puertos.

  • Un equipo que ejecute el supervisor
  • Acceso a la API local de la BBox y a NetPulse por HTTPS

UniFi self-hosted

Lee gateways, switches, puntos de acceso y clientes de un site en tu controlador.

  • Consolas UniFi OS y controladores standalone alojados por ti
  • Usuario de solo lectura en el controlador
  • Sin cuentas cloud de ui.com, CPU ni temperatura

Firmware avanzado

Un beacon dentro del switch

Los switches Realtek web-managed no ejecutan el agente Go. El fork de RTLPlayground añade un beacon que envía datos directamente al listener de NetPulse.

Qué recibe NetPulse

  • Estado y velocidad de los enlaces cada 30 segundos
  • Tasas de tráfico calculadas a partir de los octetos de cada puerto
  • Tabla FDB cada cinco minutos para localizar clientes por MAC

Qué exige

  • Un modelo incluido en la lista de dispositivos de RTLPlayground
  • Compilar el fork para tu máquina y definir el identificador del switch
  • Sustituir el firmware y disponer de copia y recuperación del flash

El beacon usa UDP con un token en claro dentro de una LAN de confianza. No usa el transporte HTTPS firmado de los agentes externos.

Solo agentes externos

Por qué van en otro repositorio

RouterOS, Asus, BBox y UniFi comparten un repositorio separado. NetPulse mantiene el contrato de ingest y cada integración sigue el ritmo de su fabricante.

Ciclos de vida separados

Una integración publica correcciones con su propia etiqueta, sin esperar a una versión del servidor.

Credenciales aisladas

La contraseña del router o controlador se queda en la configuración de la integración. NetPulse recibe el token del agente.

Solo lectura

Estas integraciones consultan y envían datos. No cambian la configuración del equipo desde NetPulse.

Transporte de agentes externos

Un contrato firmado

El agente firma cada instantánea con HMAC-SHA256 en la cabecera X-Agent-Signature y la envía al ingest de NetPulse con su token. El equipo aparece como external.

  • Un NetPulse accesible por HTTPS desde donde corra el agente
  • Un token de router creado en la app
  • Un usuario de solo lectura en el router o controlador

Compilar el supervisor

git clone https://github.com/gnacho/netpulse-integrations cd netpulse-integrations go build -o netpulse-integrations ./cmd/integrations-supervisor

El repositorio publica binarios estáticos para amd64 y arm64 con SHA-256. Incluye una unidad de systemd de ejemplo.

Límites que conviene conocer

  • Los agentes externos no configuran routers ni controladores.
  • El agente nativo sigue siendo la vía recomendada para OpenWrt y GL.iNet.
  • El beacon no informa de CPU, RAM o temperatura, y no envía la tabla LLDP.
  • Un switch alimentado por beacon no puede añadir SNMP como segunda fuente en NetPulse.
  • El beacon del fork no forma parte de RTLPlayground upstream.
